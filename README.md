# Proof packages for computer-assisted proofs — specification

A *proof package* is a self-contained, durable record of a computer-assisted
proof.
 
A typical published computer-assisted proof describes the mathematical argument and gives a
link to a source code. It sometimes does not include the data, since these might be very
large. A proof package sets an expectation on the record:
 
- the theorem,
- the finite data the proof is about,
- the program that checks the proof from that data alone.

The goal is a common base that makes computer-assisted proofs easier to
manipulate and to build upon. In particular, more readable and more
reproducible: either by running the pinned checker as it was, if it still runs;
or, if it no longer does, by reading the statement, taking the data, and
re-verifying with whatever rigorous computational resources are available at
that time.
 
**The package standardizes the format, not the content (which files exist and
what they accomplish). What is inside the data and how the checker works is the
responsibility of the authors.**

Start a package from [capsule-math/template](https://github.com/capsule-math/template)
("Use this template" on GitHub, or `gh repo create <name> --template capsule-math/template`).

## 0. Listing in the index

Open a pull request in [capsule-math/index](https://github.com/capsule-math/index)
adding `entries/<name>.json`: the package's `entry.json` plus a `location`
field (§6).

## 1. Layout

```
statement.md      the theorem, the conditions, and which inputs are frozen or produced
entry.json        title, authors, how to run the checker (and the producer)
data/             the checker's frozen inputs, and hashes.json
checker/          evaluates the conditions; exit 0 iff all hold
tools/            optional helpers shipped with the template (hash_data.jl, fetch_data.jl)
LICENSE
```

These four points are fixed: `statement.md`, `entry.json`, the checker's
output (§4), and `data/hashes.json` when any input is frozen (§3). Everything
else (file names inside `data/` and `checker/`, formats, languages, extra
folders) is up to the authors.

## 2. statement.md

The mathematics of the package.

Rules:

- States the theorem and cites the paper that proves it, if any.
- Fixes the setting the conditions live in: spaces, norms, truncation
  parameters, constants, the map(s), with pointers to where the paper defines
  them; and says what the arithmetic must provide (e.g. outward-rounded
  binary64 intervals; higher precision where used).
- Describes the inputs: what they mean (coefficients of what, on which grid, in
  which basis), which are frozen and which are produced (§3), and the byte layout
  of each frozen file, so the data can be read without the checker's language.
- Lists the conditions, numbered, each a finite statement about the inputs
  verifiable by computation and tied to a lemma of the paper, such that all
  conditions hold ⇒ theorem.

## 3. data/

The checker's inputs. Each input is either *frozen* (a file, fixed once and for
all) or *produced* (generated by a declared step). A package may use either or
both.

The producer is never trusted, only run: if it produces bad inputs, the checker
fails; it cannot make it pass wrongly. What freezing buys is that everyone
checks the same object. Freeze what is costly to produce.

Rules:

- Frozen numbers are stored bit-exactly: raw IEEE binary64/binary32, exact
  rationals, integers, or hex float strings. Never decimal printouts of floats.
  Intervals are stored as their two endpoints; floats may be stored as thin
  intervals.
- `data/hashes.json` lists every frozen file: name → `{"sha256": …}`, with an
  optional `"url"` where the file can be downloaded when it is not in the
  package (a large file kept out of git). The checker verifies the hashes before
  using the files. `tools/hash_data.jl` writes this file and
  `tools/fetch_data.jl` downloads and verifies the files listed with a url;
  any tools doing the same will do.
- The producer, if any, lives wherever the authors like (a `search/` folder,
  say) and is run by the `produce` command of `entry.json`.

## 4. checker/

A program that verifies every condition in `statement.md` on the inputs.

Rules:

- Runs from a clean environment, with dependencies declared and pinned. The
  command is `run` in `entry.json`.
- Evaluates; it does not search. Anything else it needs beyond `data/` is
  written in the checker itself.
- Prints each condition of `statement.md`, in order, with the enclosure
  obtained, prefixed `pass` or `fail`.
- Exit code 0 iff every condition holds.

## 5. entry.json

What a reader, a script or an AI needs before opening the package. See
`entry.schema.json`.

| field | |
|---|---|
| `title` | required; short name of the theorem |
| `authors` | required |
| `run` | required; the command that runs the checker, from the package root |
| `paper` | optional; journal reference with DOI, and/or arXiv id |
| `keywords` | optional; subject and method, e.g. `["three-body problem", "radii polynomial"]` |
| `produce` | optional; the command that generates the produced inputs |

## 6. Where a package lives

Anywhere public: a GitHub repository, a Zenodo record, both, or any other
link. The index records one pinned `location` per entry:

- a GitHub URL at a commit, `https://github.com/<owner>/<repo>/tree/<40-hex sha>`,
  followed by `/<folder>` when the package is one folder of a larger repository, or
- a DOI, `https://doi.org/<doi>`.

A repository holding several packages, one per folder, lists each with its own
entry and its own folder in the location.

If you want a DOI: a Zenodo record is free and permanent, and its files cannot
be changed once published. [Upload the package](https://zenodo.org/uploads/new)
(data files included), publish, and use `https://doi.org/<the DOI>` as the location.
